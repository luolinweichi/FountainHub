## 0. 这份文档是干什么的

这份文档是**开发之前唯一的事实来源**。规矩很简单：

1. 文档里没写的功能，就是不做的功能；
2. 想加功能，先改文档，再改代码；
3. 代码和文档不一致时，以文档为准（或立即改文档并记录原因）。
   📌 **2026-10-04 补**：**若实测项目（代码 / 数据库 / 路由 / 设计稿）与本文档不一致，先以实测为准**，并立即修订本文档、在变更记录写明原因。

这就是 SDD（Spec-Driven Development，规格驱动开发）的核心：**先定义清楚"做什么"，再讨论"怎么做"，最后才写代码。**

## 1. 项目背景与目标

### 1.1 现状（需求方确认）

社团目前**没有任何信息化记录体系**：

- 学员信息、学习进度、获奖情况**基本没有系统记录**；
- 日常沟通依赖群聊，信息容易被刷走；
- 考勤靠人工，需要额外整理后才能交给指导老师；
- 社团成果（获奖）没有对外展示的窗口。

### 1.2 要解决的核心问题

| 编号 | 问题 | 对应模块 |
|---|---|---|
| P1 | 学员档案散乱，想查一个人的情况很麻烦 | M2 学员档案 |
| P2 | 看不到"谁在认真练、谁掉队了" | M6 打卡热力图 |
| P3 | 没有统一的练习题渠道，学习无章可循 | M4 在线题库 |
| P4 | 获奖成果没有沉淀，也没法对外展示 | M8 获奖管理 |
| P5 | 活动通知到不了位，考勤要手工统计 | M9 新闻 + **M6 考勤**（原 M10，2026-10-03 已并入 M6） |
| P6 | 学校/指导老师要数据时拿不出来 | M11 统计与导出 |

### 1.3 一期目标（可验收）

1. 一名学员从「**自助注册（待审核）**」到「**考勤签到 + 签到日历**」、并看到自己的**绿色学习热力图**，全程无需管理员干预；
   ⚠️ **2026-10-04 实测对齐**：原文写「完成一次章节练习并看到自己的绿色打卡格」—— **一期不提供在线题库**（属二期，见 FR-6.9 与 M4/M5 的 ⏸️ 标注）；一期的对应成果是 **① 考勤签到 + 签到日历**、**② 绿色学习热力图**（P1 用测试数据、**只读、无录入入口**）；
2. 管理员能在 1 分钟内录入一条带图片的获奖记录，并决定是否对外展示；
3. 一次例行活动的考勤结果，能在 2 分钟内导出发给指导老师；
4. 系统支持 **100 人同时在线**使用，不出现明显卡顿或崩溃；
5. **计划在约半个月内上线一期**。

> 🚨 **半个月的现实警告**：按本文档全部 P0 功能，半个月**不可能**做完。建议一期只保证「**登录 → 学员档案 → 打卡热力图 → 新闻公告**」这条最小主链跑通并可演示，其余 P0 顺延到 1.5 期。否则结果通常是：延期 + 一堆半成品。

### 1.4 明确不做的事（负范围 / 边界）

写清楚"不做什么"，比写"做什么"更能防止项目失控：

| 不做的事 | 原因 |
|---|---|
| ❌ 自己实现编程题在线判题（自建 OJ） | 需要代码沙箱、防作弊、判题机，难度极高，收益低 |
| ❌ 网站内上传/播放教学视频 | 需求方明确为**二期**功能 |
| ❌ 短信验证码 | 需企业实名 + 签名审核 + 按条付费，性价比极低 |
| ❌ 微信/QQ 扫码登录 | 需第三方资质接入，一期不做 |
| ❌ 评论、点赞、学员投稿 | 需求方明确**推迟到二期** |
| ❌ 用 C++ 做后端 | 生态不适合 Web 开发，开发效率低 |
| ❌ 获奖积分排名体系 | 需求方明确不需要 |

| 角色 | 人数 | 说明 |

### 3.3 关键权限规则

- **R1 按组隔离**：组长**只能查看本组的组员姓名与人数**（`/me/group`）；**不能修改任何数据**，**无法访问其他组数据**，**无法进入任何后台页面**（`/admin/**` 一律 403）。<br>🔄 **2026-10-03（T-017）**：原为「组长只能**读写**本组学员」，项目负责人明确收窄为「**只能看，不能改，且只看姓名与人数**」。
- **R2 副社长限制**：可管理全部学员与学习内容，但**不能删除数据、不能管理账号**。
> ~~R3 后勤职责隔离~~ —— ✅ **2026-10-02 按 Q2b 的确认结果删除本条**（兼后勤社长权限与普通社长完全一致）。
- **R4 学员隐私**：学员只能看到自己的进度；**看不到任何其他学员的手机号等联系方式**。
- **R5 获奖公开需授权**：一条获奖记录只有在**学员本人同意公开**的前提下，才会出现在对外展示页。
- **R6 进度监看范围**：学习进度仅对「本人 + 本组组长 + 社长层 + 指导老师」可见。
- **R7 账号状态与登录**：只有 `ACTIVE`（在读）与 `GRADUATED`（毕业）的账号能登录；`LEFT`（离社）与 `DISABLED`（禁用）一律拒绝。
  （2026-10-02 项目负责人确认：毕业生仍可登录回来看自己的记录。对应 `UserStatus` 枚举与 `DbUserDetailsService`。）

## 6. 非功能需求

| 类别 | 要求 |
|---|---|
| **并发能力** | 支持 **100 人同时在线**。这是很小的规模，单台 2 核 2G 服务器足以支撑。 |
| **响应时间** | 普通页面在 1 秒内打开（校园网环境） |
| **安全** | 密码哈希存储；防 SQL 注入（使用参数化查询/ORM）；防 XSS；管理员操作需鉴权 |
| **隐私合规** | 手机号等个人信息最小化收集、最小化展示；获奖对外展示必须经本人同意 |
| **可用性** | 界面为中文。🔄 **2026-10-04 修订**：**本期（P1）只做电脑浏览器视口**（1440 / 1920），**移动端适配不做** —— "100 人同时在线"是**功能指标，不作为视觉/实现限制**；移动端留待后续版本 |
| **备份** | 数据库每日自动备份，保留最近 7 天 |
| **可维护性** | 代码有注释；关键逻辑有文档；一人可独立维护 |
| **成本** | 服务器 + 域名年成本控制在**几百元以内** |
