## 1. 🔒 本任务唯一、也是最重要的红线

spec 原文：「**草稿状态的新闻游客访问不到**」，而且特别注明
「**游客直接访问详情 URL 也看不到**」。

所以做了**两道过滤，一处都没少**：

| 位置 | 规则 |
|---|---|
| **列表** | 只查 `status = PUBLISHED` ✅ |
| **详情** | 🔒 **也必须是 `PUBLISHED`** —— 草稿即使被猜到 id 也 **404** ✅ |
| `isInternal` | 游客：列表看不到、详情 404；**登录后能看** ✅ |

> 💡 **为什么用 404 而不是 403**：403 等于告诉他「这里有东西、只是你不许看」——
> **连「存在」都不该暴露**，所以一律 404 ✅

## 2. 功能

## 5. 关键设计

### 5.1 为什么分页不用 Spring Data 的 `Pageable`

新闻量很小（一期几十条），而且我们要**先过滤掉 `isInternal` 再分页** ——
用 `Pageable` 反而要在数据库层做两遍过滤。**在内存里筛完再切页**最直白、最不容易错 ✅

### 5.2 ⚠️ 顺手修的一个日志噪音（真问题）

第一轮验证时，日志里出现 **2 条 ERROR** —— 都是我主动抛的「草稿 → 404」。
原因：`ResponseStatusException` 被最下面的 **catch-all** 接住，当成了「未预期的异常」❌

**这很危险**：那个 404 是**预期行为**，如果天天刷 ERROR，真出问题时就被淹没了 ✅

**修法**：加一个处理器，`ResponseStatusException` **原样 rethrow、不记日志** ✅
复验：草稿 404 ✅、已发布 200 ✅、**日志 ERROR 0 条** ✅

### ⚠️ 那 2 条「失败」的真相

| # | 我的断言 | 实际 | 结论 |
|---|---|---|---|
| 1 | 页面上应出现「共 N 条」 | 有，但我的正则太窄没匹上 | **断言太脆** ✅ |
| 2 | 不存在的路径应 404 | 返回 **302** | **不是回归** —— 那个路径不在 `permitAll` 里，**未登录时本来就跳登录** ✅（前面几轮测试里我是已登录状态，所以看到 404） |
