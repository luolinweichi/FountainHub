## 1. 目标

点进某个学员：**看详情 + 改资料 + 做账号管理**。同时把 T-007 遗留的「**细粒度权限**」真正落地。

### 权限分级（依据 docs/00 第 5 节与 docs/01 第 3.2 节权限矩阵）

| 操作 | 指导老师 | 正社长 | 副社长 |
|---|---|---|---|
| 查看详情 | ✅ | ✅ | ✅ |
| 编辑资料（账号字段 + 档案字段） | ✅ | ✅ | ✅ |
| **改角色 / 改状态** | ✅ | ✅ | 🚫 **403** |

> 权限矩阵原话：「副社长**不能删除数据、不能管理账号**」—— 改角色 / 禁用账号就属于"管账号"。

### 实现方式：两道锁

| 层 | 做法 | 作用 |
|---|---|---|
| **页面层** | `sec:authorize="hasAnyRole('TEACHER','PRESIDENT')"` | 副社长**看不到**「账号管理」那一块 |
| **服务器层** | `@PreAuthorize("hasAnyRole('TEACHER','PRESIDENT')")` | 就算绕过页面直接发请求，也会被 **403** 挡住 |

### ⭐ 本次抓到一个真 bug（T-007 埋下的）

**现象**：副社长发 POST 改状态，返回 **405**（Method Not Allowed），而不是 403。

**根因**：`@PreAuthorize` 拒绝时，Spring Security 用 `accessDeniedPage("/403")` 做的是**转发 forward**，而且**保留了原来的 HTTP 方法**。
所以一个被拒绝的 **POST** 请求会以 POST 方法转发到 `/403` —— 而 `/403` 当时只映射了 GET → **405**。

**为什么现在才发现**：T-012 之前**没有任何 POST 接口做过角色限制**，所以这个坑一直没被踩到。

**修法**：`/403` 改用 `@RequestMapping`（不限方法）→ 实测 POST 越权正确返回 **403** ✅
（已在代码注释里写明原因，避免以后有人"顺手改回 `@GetMapping`）
