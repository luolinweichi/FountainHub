## 2. 关键设计：**方案 B —— 组长是"派生身份"**

> 项目负责人 2026-10-03 定：**一个人可以同时担任几种角色**。

但当前数据库里 `users.role` 是**一列、只能存一个角色**。要支持"兼任"，原本有两条路：
- 方案 A：加一张 `user_roles` 关联表（真正的多角色）—— **要改数据库结构**，改动面大
- **方案 B（本项目采用）**：**「组长」不存进 `users.role`，而是从 `study_groups.leader_user_id` 派生出来**

### 方案 B 怎么工作

| 动作 | 实际做了什么 | 效果 |
|---|---|---|
| **指定组长** | 只把 `study_groups.leader_user_id` 设成他 | 他**下次登录时自动多一个 ROLE_LEADER** = 「加上组长角色」✅ |
| **取消组长** | 清掉 `leader_user_id` | ROLE_LEADER **自动消失** = 「减掉组长角色」✅ |
| 主角色的修改 | 还是老样子（详情页下拉） | **完全不受影响** ✅ |

### 为什么选 B（而不是加表）

1. **零数据库改动** —— 不用改表结构
2. **「谁是组长」只有一份真相** —— 就在 `study_groups` 表里。
   如果 `users.role` 也存一份，两份就会不一致（角色被降成学员，但 `leader_user_id` 还挂着他）
3. **自然支持兼任**：学员+组长、社长+组长、副社长+组长 ✅、一个人带两个组 ✅
4. T-017 的「按组隔离」天然需要这个信息

**连带的必要改动**：角色下拉框里**不再提供 LEADER** —— 见 `Role.assignable()` 的注释。

### ⚠️ 那 1 条"失败"是**我的测试期望写错了**，不是代码问题

```
FAIL 按 Python 组筛选 → 只剩 1 人   []      ← 返回 0 人
```

**原因**：我假设"当上组长 = 自动成为该组成员"。但按项目负责人的设计
「指定组长时**只是**在他的账号里加上组长角色」——**组员身份是另一件事**，
要在学员详情页的「所属组」里单独设置。

**所以那一刻 student 确实不在任何组里，返回 0 人是对的** ✅

> ✅ **项目负责人 2026-10-03 决定：要加入该组。**
> 指定某人当组长时，**顺手把他加入这个组**（如果他原本在别的组，会被**移过来**）——
> 这样才不会出现"他带着 Python 组、却在 C 语言组"的矛盾。
> **取消组长时不会把他移出组** —— 他仍然是组员，只是不再是组长。
