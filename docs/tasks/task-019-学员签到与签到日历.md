## 1. 任务理解

### 打卡 = 「你到场了没有」

学员打开 `/me/attendance`，看到三块：

1. **今天**：今天有活动就给一个【签到】按钮，点一下就签到
2. ⭐ **签到日历**：和热力图**同一种样式**，但**只有两种颜色**（签到了 / 没签到）
3. **本周活动 + 我的签到记录**

### ⭐ 项目负责人特别强调的

> 「就是看是否缺席那个，把那个设计成和热力图一个样式，但是只会有两种情况，
> 就是签到和未签到……哪一天签到了就把它换成另一个颜色，没签到就不变。
> 然后这个和学习的绿色热力图分开。」

## 5. 关键设计

### 5.1 「我哪几天签到了」怎么算出来

```
① 取我的全部签到记录（attendance_records.user_id = 我）
② 记录里只有 event_id，没有日期 → 再查这些活动，拿到 event_date
③ 只保留「近一年」且「不晚于今天」的 → 放进 Set<String>
④ 传给前端，ECharts 用它把对应格子染色
```

> 💡 **为什么不在 `checkins` 上加日期**：签到和做题是**两回事**，混在一起就又会变成
> 「我原来的错误理解」那种设计 ✅

### 5.2 🔒 三条安全设计

| 设计 | 说明 |
|---|---|
| **路径里没有 userId** | 只能签自己 —— 不是靠判断拦住，而是**压根没有「帮别人签到」这个入口** |
| **签到用 POST** | 用 GET 的话，浏览器预取 / 后退 / 别人发你一个链接，都可能**莫名多一条签到** |
| **唯一约束兜底** | 并发双击 → 数据库 `UNIQUE (event_id, user_id)` 挡掉，捕获后给友好提示（不是 500） |

### 5.3 为什么两色日历要用 visualMap.pieces

ECharts 连续的 `visualMap` 会按数值做**渐变**；
用 `pieces` 写死两个色块（0 → 浅灰、1 → 深绿），就得到「**只有两种状态**」的日历 ✅
这正是签到日历和热力图在配置上的**唯一区别**。

| 参考图的元素 | 签到日历的做法 |

| 今日学习 / 本周学习 / **累计学习 40小时37分钟18秒** | 今日签到 / 本周签到 / **累计签到 N 天** |
| 右上角 **2026年 ▼** | ✅ 可切换年份，**不刷新页面** |
| 左侧 周一/周三/周五/周日、底部 1月…12月 | ✅ 照做 |

| 底部 最长连续学习天数 / 最近一次学习 | **最长连续签到 N 周** / **最近一次签到** |

> 💡 **同一个结构也给 T-021 用** —— 换成 `checkins` 数据 + 七级绿色渐变即可。

### ⭐ 第二条修订：连续签到**只算例行活动日**

> 「连续签到只算星期三，这个星期三他来了，下个星期三他也来了，这个就叫连续签到。
> **不需要每天都要，毕竟我们中学生是有主业的。** 当然如果他每天就来了，也可以写鼓励。」

```
把全部 WEEKLY_MEETING 按日期排序，从最近的往回数：
  · 这次例行活动来了      → 计数 +1，看上一次
  · 哪次没来      → 【停下】
  · 那场是【未来】的  → 【跳过】← 不然未来的例行活动日会把连续误判为断
```

**鼓励文案**（后端算好，改文案只改一处）：

| 情况 | 文案 |
|---|---|
| 连续 ≥ 5 周 | 「连续 N 周例会全勤，很了不起 🔥」 |
| 连续 3~4 周 | 「连续 N 周没缺过例会，稳！」 |
| 连续 1~2 周 | 「好的开始 👏 继续保持」 |
| 连续 0 周 | 「这周重新开始，来吧 💪」 |
| **本周有活动的日子天天都来** | **额外加一句**「这周有活动的日子你天天都来了，真拼！💪」 |
