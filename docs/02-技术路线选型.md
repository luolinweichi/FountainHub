## 1. 先扫盲：一个网站到底由哪几块组成

把网站想象成一家**餐厅**：

| 餐厅里的角色 | 网站里对应的东西 | 你熟悉的类比 |
|---|---|---|
| 门面、菜单、餐桌 | **前端**（HTML / CSS / JavaScript） | 顾客直接看到的一切 |
| 后厨、厨师 | **后端**（服务器程序） | 真正干活的地方，比如你写的 C++ 程序 |
| 仓库、账本 | **数据库** | 就是你们数据结构课上的"存储" |
| 服务员 | **HTTP / 接口** | 前端和后端之间的传菜员 |
| 店面的房子 | **服务器** | 一台 24 小时开机的电脑 |

**关键认知**：你写的代码 = 后厨的厨师。你做这个项目，**主要工作是在后厨**（后端）+ 摆盘（页面样式）。

## 2. 主流网站实际在用什么（真实数据）

### 2.1 全世界网站的服务端语言占比

数据来源：[W3Techs 统计](https://w3techs.com/technologies/history_overview/programming_language/ms/y)（2026 年 10 月抓取）

| 语言 | 约占全网网站比例 |
|---|---|
| PHP | **约 70%～80%** |
| JavaScript（Node.js） | 约 7% |
| Ruby | 约 7% |
| Java | 约 5% |
| ASP.NET（C#） | 约 4% |

> ⚠️ **这张表非常容易误导人**，必须解释：分母是"全世界所有网站"，里面塞满了 WordPress 建的企业官网、十几年前的老站、个人博客。**PHP 高不是因为新项目都选 PHP，而是因为老网站基数巨大。**

### 2.2 具体的大公司在用什么（据公开技术分享）

| 产品 | 主要后端 | 数据库 |
|---|---|---|
| Instagram | Python（Django） | PostgreSQL |
| Spotify | Python + Java | PostgreSQL |
| YouTube | Python + C++ | MySQL |
| Dropbox | Python | MySQL |
| Reddit | Python | PostgreSQL |
| 豆瓣 | Python | MySQL |
| 知乎 | Python（早期）→ 现 Python + Go | MySQL |
| 哔哩哔哩 | Go + Java | MySQL / TiDB |
| 淘宝 / 支付宝 | Java | OceanBase / MySQL |
| 微信 | C++（自研框架） | 自研 |

**前端**：全世界主流选择是 **React** 和 **Vue**（两大阵营）。

### 2.3 从这张表该读出什么

1. **大厂都是"多语言混合"**——没有一个产品只用一种语言。
2. **Python 在"中等规模、快速开发"这个区间几乎是绝对王者**（Instagram、Spotify、Reddit、豆瓣、知乎早期全都用它）。
3. **数据库层面 PostgreSQL 和 MySQL 平分天下**，PostgreSQL 近年持续上升。
4. **大厂用 Java/Go/C++ 是为了扛亿级流量**，你们 100 人，跟这个需求完全不在一个量级。

## 3. 为什么"主流 ≠ 适合你"

这是个非常重要的思维转换：

| 大厂选型时的考虑 | 你选型时该考虑 |
|---|---|
| 能不能扛住 10 亿用户 | 我能不能在半个月内学会 |
| 几百个工程师怎么协作 | 只有我一个人维护 |
| 招人好不好招 | 出问题了我能不能自己修 |
| 性能极限压榨 | 100 个人同时用，别崩就行 |

> **结论：你要的是"学习成本最低 + 一个人能跑起来"，而不是"最主流"。**

## 4. 四条路线，用大白话对比

> ⚠️ **2026-10-04 加注（本节是决策留痕，请配合文首"最终结论"块读）**
> 1. 本节**当时推荐路线 A（Python + FastAPI）** —— **最终被否决**，实际采用**路线 C**（见 §9）。
> 2. 本节多处计划用 **ECharts** 画学习热力图（下面路线 A 的零件清单、§5 第 4 条都有）。
>    **实际实现已弃用 ECharts**：改为**服务端渲染的纯 CSS 格子**（14px 格 / 3px 间距 / 3px 圆角）。
>    原因：ECharts 要引 CDN，历史上**出现过白屏**（项目负责人反馈"灰格子看不见 / 图是空白"）；
>    CSS 格子不依赖 CDN/JS，**永远不会白屏**，且可逐格核对。（见 [08-视觉与品牌规范](08-视觉与品牌规范.md) §10 约束 6）
> 3. **原文一字未删**，只加这段注。

### 路线 A：Python + FastAPI ⭐ 推荐

**零件清单**：

| 零件 | 作用 | 学习难度 |
|---|---|---|
| Python 语法 | 写后端逻辑 | ⭐（你会 C++，2～3 天） |
| FastAPI | Web 框架，负责接收请求 | ⭐⭐ |
| SQLite → MySQL | 数据库 | ⭐（SQL 很简单） |
| Jinja2 模板 | 把数据填进 HTML 页面 | ⭐ |
| Bootstrap | 现成样式库，不用自己写 CSS | ⭐ |
| ECharts | 画那张绿色热力图（**自带日历热力图**） | ⭐ |

**优点**：学的东西最少；不需要学前端框架；Python 语法对你来说极其轻松；AI 辅助写 Python Web 的成功率最高。
**缺点**：管理后台的"增删改查"要自己写（大约几十个页面，但每个都是同一个套路）。

### 路线 B：Python + Django

**和 A 的区别**：Django 是"大而全"的框架，**自带一个现成的管理员后台**——你几乎不用写后台页面，配一下就能增删改查学员、获奖、新闻。

| | 路线 A | 路线 B |
|---|---|---|
| 后台页面 | 自己写 | **框架白送** |
| 要学的概念 | 少 | 多（ORM、App、Settings、Admin 定制） |
| 出问题排查 | 容易，代码都是你写的 | 较难，得先懂框架 |
| 灵活度 | 高 | 受框架约束 |

**取舍**：如果你只想**最快出一个能用的系统**，B 反而更快；如果你想**真正学会 Web 开发**，A 更扎实。

### 路线 C：Java + Spring Boot
企业级方案，配置繁琐（一个项目要配十几个文件），开发速度慢。**你的 Java 只是为了用 AI 做过一次网站，不建议。** 除非你想走"Java 后端工程师"的职业路线。

### 路线 D：Node.js + Express + React 前后端分离
最现代，但你要**同时学** JavaScript、React、接口设计、状态管理——四座山一起爬。**半个月绝对来不及。**

### 一条必须排除的路线：C++ 写后端
你 C++ 很强，但 C++ 的 Web 生态极其贫瘠（框架老、轮子少、字符串处理痛苦）。**不要因为"我会 C++"就选 C++**，这是新手最容易踩的坑。

## 5. 我的最终推荐（附理由）

> ⚠️ **2026-10-04 加注**：本节的"首选：路线 A"是**选型当时的推荐，已被否决**；
> 需求方最终选择**路线 C（Java + Spring Boot）**，理由与代价见 **§9**。
> 下面的理由 1~3、5 属于通用考量（时间 / 底子 / 不碰前端框架 / AI 效率）；
> **理由 4「热力图有现成方案（ECharts）」在实际实现中不成立** —— ECharts 因 CDN 白屏问题**已被弃用**，改纯 CSS 格子。

**首选：路线 A。备选：路线 B。**

理由排序：

1. **时间**：半个月，A 的学习曲线最平缓；
2. **你的底子**：CSP-S 二轮 100+ 说明逻辑能力极强，Python 语法对你是降维打击，**瓶颈不在算法，而在"Web 概念"**，A 需要学的概念最少；
3. **不需要碰前端框架**：服务端直接生成 HTML，Bootstrap 解决样式，**你几乎不用写 CSS**；
4. **热力图有现成方案**：ECharts 的日历热力图就是 GitHub 那个样式，配置代码可以直接抄；
5. **AI 辅助效率最高**：Python Web 是资料最丰富的领域。

## 6. 选 A 之后，你要按顺序学这 7 样

| 顺序 | 学什么 | 用途 | 预计时间 |
|---|---|---|---|
| 1 | Python 基础语法 | 写逻辑 | 2～3 天 |
| 2 | HTTP 基础（GET/POST、状态码、Cookie） | 理解"网页怎么工作的" | 半天 |
| 3 | SQL 基础（增删改查、JOIN） | 操作数据库 | 1～2 天 |
| 4 | FastAPI 入门（路由、参数、返回） | 写出第一个接口 | 2 天 |
| 5 | Jinja2 模板 + Bootstrap | 把数据变成好看的页面 | 2 天 |
| 6 | 登录与权限（Session、密码哈希） | 做权限系统 | 2 天 |
| 7 | 部署（Linux、Nginx、域名） | 让别人能访问 | 3～5 天 |

**总共约 2～3 周的学习量**——正好和你的"半个月"目标冲突，这也是我在需求文档里发出警告的原因。

> 💡 **务实建议**：不必"学完再写"。**边学边写，我带你一模块一模块地做**，学得最快。

## 9. 最终决定：路线 C（Java + Spring Boot）

**需求方于评审后决定采用路线 C**，本文档第 5 节的推荐（路线 A）未被采纳。此处记录决定及其影响，供后续追溯。

### 9.1 为什么这个决定是合理的

- Java 生态极其成熟，资料、招聘、社区都是顶级；
- 对**长期发展**有利（若未来想走后端工程师路线，Java 是硬通货）；
- 需求方此前用 Java + AI 做过一个网站，**有成功经验**，心理门槛低；
- Spring Boot 的「约定优于配置」已大幅简化传统 Java Web。

### 9.2 必须提前知道的代价

| 方面 | 现实情况 |
|---|---|
| 样板代码 | 比 Python 多 2～3 倍，一个简单功能要写 Entity / Repository / Service / Controller 四层 |
| 学习曲线 | 要理解**依赖注入、注解、Bean 生命周期**等概念，前期会有「代码在跑但我不知道为什么」的阶段 |
| 启动速度 | 每次改代码重启较慢（可用 DevTools 缓解） |
| 半个月上线 | ⚠️ **基本不可能完成全部 P0**，需要砍范围或延到 3 周 |

### 9.3 Java 路线专属学习清单

> ℹ️ **2026-10-04 实际对照**：这份清单是"决定走 Java 后要补的东西"。
> 实际执行中，**第 2/3/4/5/6/8/9 项都真的用上了**（Maven 3.9.15、Spring Boot 3.3.5、Spring MVC、
> Thymeleaf + Bootstrap 5.3.3、Spring Data JPA、Spring Security + BCrypt、文件上传）。
> ⚠️ 第 10 项「打包部署」**还没做**（T-039 被"暂不装运行环境"阻塞、T-040 代码同步方案未定）。

| 顺序 | 学什么 | 预计时间 |
|---|---|---|
| 1 | Java 语法速通（对比 C++：无指针、有 GC、类/接口/泛型/集合/注解） | 3～4 天 |
| 2 | Maven 与标准项目结构 | 1 天 |
| 3 | Spring Boot 核心（注解、依赖注入、配置文件） | 3 天 |
| 4 | Spring MVC（Controller、路由、参数绑定） | 2 天 |

| 9 | 文件上传 | 1 天 |
| 10 | 打包部署（jar + Nginx + systemd） | 3 天 |

**合计约 3 周**。建议：不必学完再动手，**边做边学**。
