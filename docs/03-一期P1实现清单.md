> **P1 = 社团内部真正能天天用起来的最小闭环。**

## 1. 为什么现在就该谈 P1

Java + Spring Boot 的样板代码是 Python 的 2～3 倍。如果一上来什么都做，结果一定是**三个月后什么都还没上线**。

所以 P1 的核心动作是：**砍**。砍掉一切"以后可以加"的东西，只留主干。

### M1 账号与登录

**做什么**
- 学员**自助注册**（公开页 `/register`；原计划「管理员在后台建号」已于 2026-10-02 变更，`/admin/students/new` 实测无此路由）
- 管理员在 `/admin/students` **审核入社申请**（通过 / 拒绝），并在**学员详情页**调整角色与状态
- 登录页：**学号 / 手机号 / 用户名 任选其一 + 密码**
- 密码用 BCrypt 加密存储（Spring Security 自带）
- 角色：指导老师、正社长、副社长、组长、学员（**共 5 种**；原文列的「社长(兼后勤)」2026-10-02 已并入社长层，不单设）
- 未登录访问后台 → 自动跳登录页
- 越权访问 → 返回 403 页面
- 忘记密码 → ✅ **已完成**（T-012B，2026-10-04）：登录页「忘记密码」入口 → `/forgot` 提交申请 → 社长在 `/admin/students` 审核，**通过后新密码才生效**（全流程不出现"重置"二字）

**验收标准**
1. 用学号、用户名、手机号三种方式都能登录同一个账号 ✔
2. 数据库里看不到明文密码 ✔
3. 组长访问其他组的学员详情，被拒绝 ✔
4. 未登录访问 /admin/** 被跳转到登录页 ✔

## 5. ⚠️ 关键缺口：打卡的数据从哪来（这就是 Q5）

你原本的设计是：**学员做题 → 系统自动记录 → 热力图有数据**。

但 P1 把**题库砍掉了**，于是出现一个空档：

> ⚠️ **本表已作废（2026-10-04 对齐）**：当时讨论的是「打卡数据从哪来」，三个方案（X 自助 / Y 管理员录入 / Z 混合）**最终都没有采用** ——
> 一期**不提供任何自助录入**（热力图 `/me` 只读、无入口，P1 用测试数据），数据将由**二期题库**写入 `checkins`；
> 而「打卡」这件事已澄清为**考勤签到**（`/me/attendance`），与热力图是两回事。以下仅作决策留痕。

| 方案 | 说明 | 优点 | 缺点 |
|---|---|---|---|
| **X. 自助打卡** | 学员自己填"今天做了 N 题" | 立刻能用，实现最简单 | 可能虚报 |
| **Y. 管理员录入** | 社长每周批量填 | 数据准 | 你工作量大 |
| **Z. 混合** | 学员自助填 + 社长可修正 | 平衡 | 需要两个入口 |

> **我的建议：先做 Z（混合）**。
> 一期先用"自助 + 社长修正"撑住热力图；等二期题库上线后，**数据自动产生**，自助入口降级为补充手段。
>
> **这样设计的好处**：打卡表结构从第一天就是通用的（学员ID + 日期 + 数值 + 指标类型 + 来源），
> 题库上线时**不用改表、不用改页面**，只是多了一个数据来源而已。

### Q5 的解决方案（已定，可随时改）

由于题库移到 P2，**一期热力图没有自动数据来源**（用直接插入的测试数据验证效果）；「打卡」= **考勤签到**，走 `attendance_records`。因此：

- ⚠️ **2026-10-04 实测对齐**：**「学员自己填今天做了几道题」从未实现，也不再需要** —— 热力图**只读、页面上没有任何录入入口**（`MyHomeController` 只有 GET）。下面第 1 条是 2026-10-02 的方案原文，保留作历史：
- ~~**一期界面**：学员只填「今天做了几道题」（最简单，不让学员填复杂表单）~~
- **表结构**：一天允许存在**多条不同指标类型**的记录（题数 / 学习时长 / 章节完成数）
  - P1 **不写入**任何指标（热力图用直接插入的测试数据验证）；
  - P2 题库上线后，系统自动写入「题数」（`PROBLEM_COUNT` / `source=QUIZ`，见 [10-题库API契约](10-题库API契约.md)）；
  - 将来有教学视频，再写入「学习时长」，**表结构和热力图都不用改**。
- **来源标记**：每条记录带 source 字段（MANUAL / QUIZ / OJ / ADMIN），便于以后区分数据可信度。

> ✅ 结论：**不需要你现在拍板**。设计成通用的，三种口径以后都能装进去。
